Hyper-V GPU-P 與本地 AI 技術探索

讓虛擬機器使用實體 GPU：從配置失敗到驅動修復。

Windows Server 2025Hyper-VGPU-PPowerShellNVIDIACUDA / Ollama 探索

我嘗試在 Windows Server 2025 的 Hyper-V 環境中，將 NVIDIA GeForce RTX 4070 Ti SUPER 的 GPU 資源提供給虛擬機器。實作涵蓋 GPU 分割配置、虛擬機器調整、顯示驅動相容性排查，以及後續的遠端操作與本地 AI 探索。

開發與測試環境

主機：Windows Server 2025
GPU：GeForce RTX 4070 Ti SUPER
虛擬化：Hyper-V / Generation 2 VM
工具：PowerShell、事件檢視器、裝置管理員
延伸：RDP 相對滑鼠、CUDA、Ollama

研究問題

虛擬機器如何取得可用 GPU 資源？GPU 分割配置為何啟動失敗？當 Guest GPU 出現 Code 43，如何利用事件紀錄定位問題？Host 與 Guest 驅動版本有何影響？

關鍵除錯過程

01 · GPU 分割與啟動失敗

配置階段遇到 0x800705AA（系統資源不足）及 Hyper-V-VMMS Event 34520。依據事件內容檢查 GPU-P 資源設定與裝置指派政策。

02 · Guest 顯示卡初始化異常

Guest 裝置管理員顯示 NVIDIA Code 43，並記錄到 DxgKrnl Event 549 / StartAdapter_AddAdapterFailed。進一步排查 Guest 驅動檔案完整性與 Host 版本相容性。

03 · 驅動修復成功

將 Host 上 NVIDIA 591.59 的完整驅動目錄複製至 Guest 並完成相應配置後，Code 43 與 Event 549 消失，Guest 得以正常使用 GPU-P。此為本專案的重要突破。

04 · 延伸探索與限制

進一步研究 VMConnect／RDP 相對滑鼠、CUDA 與 Ollama。尚未提供的模型推論或效能數據不列為已驗證成果。

故障紀錄摘要

VM 啟動：0x800705AA
VMMS：Event 34520
Guest GPU：Code 43
DxgKrnl：Event 549

修復結果

Code 43 與 Event 549 消失；Guest GPU-P 可使用。重點是以修復前後紀錄驗證假設，而非僅重複套用指令。

個人貢獻與技術定位

親自進行環境配置、測試、錯誤紀錄與故障排查。主要使用 PowerShell 管理 VM 與 GPU-P，並非從零撰寫 GPU 虛擬化驅動。正式送件時應補充外部教學來源、AI 輔助範圍及自己完成的步驟。

2026/11/09 · CUDA 實際運算驗證成功

在 Hyper-V Generation 2 Guest 內，使用 NVIDIA 591.59 驅動與 PyTorch 2.11.0+cu128 進行 CUDA 測試。torch.cuda.is_available() 回傳 True，辨識到 NVIDIA GeForce RTX 4070 Ti SUPER，並成功執行兩個 2048 × 2048 隨機矩陣的 GPU 乘法與同步作業。

實際輸出：GPU matrix multiplication: SUCCESS；該次結果校驗值 90926.625（隨機資料結果，非效能指標）。測試初期曾遇到缺少 Visual C++ 執行階段導致的 WinError 126，安裝 Microsoft Visual C++ Redistributable 後成功載入 PyTorch。仍有缺少 NumPy 的非致命警告。

這項測試證實 Guest 可執行 PyTorch CUDA 矩陣運算；尚未進行效能基準測試或 AI 模型推論效能驗證。待補實際終端機截圖。

DEVELOPMENT JOURNEY · 技術探索歷程

從零架設虛擬機器，到成功實現 GPU-P

從最初對虛擬機器的好奇，到利用事件紀錄與驅動測試，逐步排查 GPU 初始化問題。

起點｜為什麼想研究虛擬化？

最初我只知道虛擬機器能在一台電腦中執行另一個作業系統。當我接觸 Hyper-V 後，開始思考：既然 VM 可以分配 CPU、記憶體與儲存空間，是否也能使用主機的 RTX 4070 Ti SUPER？這個問題讓我開始探索 GPU-P。

第一階段｜建立 VM 與理解開機架構

在 Windows Server 2025 上建立 Hyper-V 虛擬機器，接觸 Generation 1、Generation 2 的差異，並處理虛擬硬碟、MBR/GPT、UEFI 與磁碟分割問題。這讓我理解，建立 VM 不只是安裝 Windows，更需要理解系統如何啟動與管理資源。

第二階段｜GPU-P 配置失敗

使用 PowerShell 查詢可分割 GPU、建立 GPU Partition Adapter 後，遇到 0x800705AA 與 VMMS Event 34520。從這時起，我不再只看錯誤訊息的表面文字，而是開始檢查資源配置、系統政策及事件紀錄，逐步縮小問題範圍。

第三階段｜追查 Code 43 與 Event 549

VM 取得 GPU 資源後，Guest 內的 NVIDIA 裝置仍顯示 Code 43，DxgKrnl 也記錄 Event 549（StartAdapter_AddAdapterFailed）。我將注意力轉向 Host 與 Guest 的驅動版本及檔案完整性，反覆測試不同配置。

關鍵突破｜完整配置 NVIDIA 591.59 驅動

將主機端 NVIDIA 591.59 的完整驅動目錄複製到 Guest 並完成相應配置後，Code 43 與 Event 549 消失，GPU-P 終於能正常使用。這次成功讓我體會到：技術問題的突破，往往來自完整紀錄、合理假設與反覆驗證。

後續探索｜遠端輸入、CUDA 與本地 AI

在 GPU-P 成功後，我繼續研究 VMConnect 與 RDP 相對滑鼠、遊戲視角限制，以及 CUDA 和 Ollama 的使用環境。這些經驗讓我看到虛擬化、驅動、圖形運算與 AI 之間的關聯；尚未完成的效能測試不會列為已驗證成果。

我的學習反思

我從一開始依靠文件與教學完成設定，逐漸學會用錯誤代碼、事件紀錄和設定差異定位問題。這個專案最大的收穫，不只是讓虛擬機器使用 GPU，而是建立了面對未知系統問題時，能夠提出假設、設計測試並驗證結果的能力。

此為個人實驗紀錄。特定 GeForce GPU-P 配置不代表官方支援；結果可能受硬體、驅動與系統版本影響。
